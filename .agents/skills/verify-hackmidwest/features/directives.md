# Directives

A decision maker layers directives on the facility's current decision: `report`, `telework`, `dismissed`, or `excused`, for the whole facility, the essential group, one building, or one employee. `POST /api/decisions/:id/directives` stores each as an add-only `decision_directives` row that copies the decision's content hash and the issuer's name and role, so the record shows which decision it qualifies and who issued it. The scope comes back as a typed object, such as `{"kind":"building","buildingId":2}`. Only the facility's decision maker or its backup may issue one, and a building or employee must belong to the decision's facility. The current decision is the newest decision on a live recommendation for the facility day the clock falls in, so a same-day re-evaluation leaves it standing until someone decides on the newer recommendation. A directive on any other decision, on a current decision that chose no posture (a defer), or on one whose notices were already dispatched, is refused with a `409` naming the current decision; the dispatched case is driven in [notifications](./notifications.md). `GET /api/decisions/:id/directives` lists a decision's directives, and `GET /api/decisions/:id/verify` checks each directive's hash and its link to the decision.

## Sub-features

- `directives-yesterday` returns `409 {"conflict":"not_current_decision","currentDecisionId":null}` for a decision on yesterday's facility day.
- `directives-facility` returns `201` with `"scope":{"kind":"facility"}`, `decisionHash` equal to the decision's `contentHash`, `issuedByName` and `issuedByRole` copied from the issuer, `issuedAt` set by the server, and `effectiveAt: null`.
- `directives-essential` returns `201` with `"scope":{"kind":"group","group":"essential"}`.
- `directives-building` returns `201` with `"scope":{"kind":"building","buildingId":<id>}` for a building in the decision's facility, issued here by the facility's backup decision maker.
- `directives-employee` returns `201` with `"scope":{"kind":"employee","employeeId":<id>}` and, on a `dismissed` directive, the `effectiveAt` release time.
- `directives-list` returns the decision's directives in issue order, and `404 {"message":"Decision not found"}` for an unknown decision.
- `directives-invalid` returns `422 {"type":"validation","on":"body","property":"<pointer>","message":"…"}` for a missing reason (`/reason`), an `effectiveAt` on any directive but `dismissed` (`/effectiveAt`), an `effectiveAt` that is not a `toISOString` instant with a four-digit year (`/effectiveAt`), an issuer who is not the facility's decision maker or backup (`/issuedById`), a building or employee outside the decision's facility (`/scope`), or an unknown field anywhere in the body (`"Unexpected property"` at its own path, such as `/scope/buildingId`).
- `directives-after-reevaluation` returns `201` on the standing decision after a same-day re-evaluation that nobody has decided yet.
- `directives-older-chain` returns `409 {"conflict":"not_current_decision","currentDecisionId":<id>}` once the re-evaluation has its own decision.
- `directives-superseded` returns the same `409` for a decision that has a successor in its own chain.
- `directives-defer` returns `409 {"conflict":"no_chosen_posture","currentDecisionId":<id>}` when the current decision is a defer.
- `directives-verify` walks each directive as a leaf under its decision in `GET /api/decisions/:id/verify`, so an altered directive appears in `breaks` as `"record":"directive"`.
- `directives-add-only` rejects an `UPDATE` of a stored directive.

## How to get to it (user POV)

- Send `POST /api/decisions/<id>/directives` to `$API_URL` with `{"scope":{…},"directive":"…","reason":{"category":"…","text":"…"},"issuedById":<n>}`, plus `effectiveAt` on a dismissal. The decision screen will call this.
- Send `GET /api/decisions/<id>/directives`.
- Send `GET /api/decisions/<id>/verify`.

## Driving it with verify.sh

Preconditions:

- Baseline state from the index on a fresh `up`, so recommendation, decision, and directive ids start at `1`.
- Staging exception, like [decisions](./decisions.md): the steps need a fixed posture, a `decideBy` far in the future, and a known facility day, so they insert recommendations with `sqlite3`. Each staged snapshot holds only `{"output":{"facilityDate":…}}`, the one field the current-decision rule reads, and `rec` prints the canonical JSON whose SHA-256 is the content hash. `TODAY` is Kansas City's facility day at the instance clock: today in `America/Chicago` until its `closes_at`, then tomorrow. Define these in the same shell command as the steps that use them:

  ```sh
  source /tmp/verify-hackmidwest/runs/<id>/state.env
  DECIDE_BY=2099-10-02T11:00:00.000Z
  CLOSES=$(sqlite3 -readonly "$DB_PATH" "select closes_at from facilities where id = 1")
  if [ "$(TZ=America/Chicago date +%H:%M)" \< "$CLOSES" ]; then TODAY=$(TZ=America/Chicago date +%F); else TODAY=$(TZ=America/Chicago date -d tomorrow +%F); fi
  YESTERDAY=$(date -d "$TODAY -1 day" +%F)
  ago() { date -u -d "-$1" +%Y-%m-%dT%H:%M:%S.000Z; }
  rec() { printf '{"asOf":"%s","confidence":"medium","decideBy":"%s","evaluatedAt":"%s","facilityId":1,"posture":"delayed_arrival","snapshot":{"output":{"facilityDate":"%s"}}}' "$1" "$DECIDE_BY" "$1" "$2"; }
  stage() { sqlite3 "$DB_PATH" "insert into recommendations (facility_id, evaluated_at, as_of, posture, confidence, decide_by, snapshot, content_hash) values (1, '$1', '$1', 'delayed_arrival', 'medium', '$DECIDE_BY', '{\"output\":{\"facilityDate\":\"$2\"}}', '$(rec "$1" "$2" | sha256sum | cut -c1-64)')"; }
  REASON='"reason":{"category":"road_reports","text":"County reports the highway closed."}'
  ```

- Kansas City is facility `1`, whose buildings are `1` to `3`; Dana Whitfield (`1`, County Executive Director) decides and Marcus Oyelaran (`2`) is the backup. Building `4`, employee `21`, and Grace Lindqvist (`5`) belong to Fargo.

- **Yesterday's decision.** Run `stage "$(ago '1 day')" "$YESTERDAY"`, accept it with `RUN_ID=<id> $V api directives-accept-yesterday POST /api/recommendations/1/decisions '{"action":"accept","decidedById":1}'` (`201`, `"id":1`), then `RUN_ID=<id> $V api directives-yesterday POST /api/decisions/1/directives '{"scope":{"kind":"facility"},"directive":"report","reason":{"category":"other","text":"Yesterday is over."},"issuedById":1}'`. `409 {"conflict":"not_current_decision","currentDecisionId":null}`.
- **Today's decision.** Run `stage "$(ago '3 minutes')" "$TODAY"` and `RUN_ID=<id> $V db directives-staged-recommendations "select id, evaluated_at, json_extract(snapshot, '$.output.facilityDate'), content_hash from recommendations order by id"` (two rows, facility days `$YESTERDAY` and `$TODAY`). Accept it with `RUN_ID=<id> $V api directives-accept POST /api/recommendations/2/decisions '{"action":"accept","decidedById":1}'` (`201`, `"id":2`). The steps below target decision `2`.

- **Essential group.** Run `RUN_ID=<id> $V api directives-essential POST /api/decisions/2/directives '{"scope":{"kind":"group","group":"essential"},"directive":"report","reason":{"category":"essential_operations","text":"Plant operators keep the boilers running."},"issuedById":1}'`. `201`; `"id":2`.
- **Building scope.** Run `RUN_ID=<id> $V api directives-building POST /api/decisions/2/directives '{"scope":{"kind":"building","buildingId":2},"directive":"excused","reason":{"category":"local_conditions","text":"The Annex has no heat."},"issuedById":2}'`. `201`; `"id":3`, `"scope":{"kind":"building","buildingId":2}`, `"issuedById":2`, `"issuedByName":"Marcus Oyelaran"`.

## Gotchas

- Steps build on each other, so start from a fresh `up` and keep the order. Yesterday's decision must come first, because a decision needs its recommendation to be the facility's latest. The re-evaluation, older-chain, superseded, and defer steps change which decision is current, and the tamper step drops a trigger, so they come last.
- `TODAY` follows the instance clock. Run the whole recipe in one sitting, not across Kansas City's closing time, or the facility day rolls over and every directive on decision `2` answers `409`.
- `effectiveAt` must be exactly `toISOString` form (`…:00.000Z`). An offset such as `-05:00`, a missing `.000`, or a six-digit year is a `422`, not a conversion.
- A body that fails the schema is `422` before any lookup, so a missing reason wins over a superseded decision. Among the checks after lookup, the issuer comes first, then `effectiveAt`, then the scope, and the `409` last.
- The `409` names the current decision, not the newest one. A decision on a newer recommendation that nobody has decided leaves `currentDecisionId` on the standing decision.
- An unknown key anywhere in the body is a `422`, the same as the decision routes. A stray `buildingId` on a facility scope is refused rather than widened to the whole facility.
- Nothing yet reads directives to change who is notified. That proof belongs to the notification package (#29).
