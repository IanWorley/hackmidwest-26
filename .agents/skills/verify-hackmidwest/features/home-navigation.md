# Home page

The home page `/` shows each facility's standing under the heading `Facility standing`. A status line counts the facilities whose shown recommendation nobody has accepted or overridden yet (`Decisions needed: <n>`). The table `Facility standing` has one row per facility: its name as a link to `/facilities/<id>`, the posture in effect (`Normal operations`, `Delayed arrival`, `Early dismissal`, `Unscheduled telework`, `Full closure`, or `Not evaluated`), which is the facility's current decision's posture once one is accepted or overridden today, with `Recommended: <posture>` when the shown recommendation differs and `As of <time> UTC`, when it was evaluated, the time left to decide (`Decide in 2 h 11 min`, `Decision overdue`, or `—` when there is nothing to decide), and `Decision needed`, the decision status (`Accepted`, `Overridden`, `Deferred`, or `Missed decision`), or `—` when not evaluated. A `View conditions` link opens `/conditions`. Every page has a header whose `Hack Midwest` link returns home and whose `Conditions` and `Facilities` links open those pages. No page links to `/tasks`; it is reached by URL.

## Sub-features

- `home-standing` shows the table with every facility `Not evaluated` and `Decisions needed: 0` on a fresh seed.
- `home-earlier-day` shows a facility whose only live recommendation is for an earlier facility day as `Not evaluated` and leaves it out of the count, so yesterday's call never reads as today's.
- `home-decision-needed` counts a facility with a new recommendation and shows its posture, countdown, and `Decision needed`.
- `home-decision-recorded` drops a facility from the count once its recommendation is accepted or overridden, and shows `Accepted` or `Overridden` with no countdown; a deferred or missed decision still counts.
- `home-missed-decision` keeps a facility in the count once its deadline passes with no decision: the row reads `Decision overdue` and `Decision needed`, and when the next evaluation records the backup decision maker's `no_decision` on the missed recommendation, the new recommendation still counts.
- `home-reevaluated` keeps an earlier same-day accept or override in effect after a re-evaluation nobody has decided on yet: the row shows the decided posture, `Recommended: <new posture>` when it differs, the new recommendation's countdown, and `Decision needed`, and the facility counts again.
- `home-refresh` updates an open dashboard within a minute, with no reload, after a recommendation is stored, and keeps refreshing from the load-error view so it recovers on its own.
- `home-deferred` shows a deferred facility as `Deferred`, counting down to the deferral's recheck time, and keeps it in the decisions-needed count.
- `home-facility-link` follows a row's facility name client-side to `/facilities/<id>`.
- `home-conditions-link` follows `View conditions` client-side to `/conditions`, and the browser fetches `GET /api/map`.
- `home-header-link` returns to `/` from any page through the header link `Hack Midwest`.
- `home-load-error` shows the alert `Facility standing could not be loaded.` when the map API fails or is unreachable.

## How to get to it (user POV)

- Open the web root `$WEB_URL/`.
- Choose a facility name in the `Facility standing` table.
- Choose `View conditions`.
- Choose `Hack Midwest` in the header from any page.

## Driving it with verify.sh

Preconditions:

- Baseline state from the index (the 4 demo facilities, no recommendations).

- **Open home.** Run `RUN_ID=<id> $V browser goto / expect table "Facility standing" snap home-standing`. `home-standing.aria.yml` has title `Hack Midwest`, navigation `Main` with links `Hack Midwest`, `Conditions`, and `Facilities` (no `Tasks`), heading `Facility standing`, link `View conditions` (`/url: /conditions`), `status: "Decisions needed: 0"`, and rows `Fargo Service Center`, `Kansas City Area Service Center`, `Lafayette Service Center`, `Yakima Service Center` in that order, each reading `Not evaluated — —`.
- **Earlier day.** Stage a live Lafayette (`4`) recommendation for yesterday's facility day with the decision-screen recipe's earlier-day staging (an `asOf` preview from yesterday noon Chicago time copied as a live row with its hash recomputed; see [decision screen](./decision-screen.md), using `home-earlier-preview` as the `api` name). Run `RUN_ID=<id> $V db home-earlier-row "select id, evaluated_at = as_of as live, json_extract(snapshot, '$.output.facilityDate') as facility_date, posture, decide_by from recommendations where facility_id = 4 order by id"`: the newest row is live and its facility date and `decide_by` are yesterday's. Then `RUN_ID=<id> $V browser goto / expect-text "Decisions needed: 0" snap home-earlier-day`. The Lafayette row still reads `Not evaluated — —`, and nothing reads `Decision overdue`. Run it before any live Lafayette evaluation, because a later live row replaces the staged one as Lafayette's latest.
- **Decision needed.** Create a recommendation, then reload. Run `RUN_ID=<id> $V api home-rec POST /api/facilities/1/recommendations` (`201 Created`), then `RUN_ID=<id> $V browser goto / expect-text "Decisions needed: 1" snap home-decision-needed`. `home-decision-needed.aria.yml` has `status: "Decisions needed: 1"` and row `Kansas City Area Service Center <posture label> As of <date>, <time> UTC Decide in … Decision needed`, where the posture label matches the `posture` in `home-rec.http.txt`. The other rows still read `Not evaluated — —`.
- **Decision recorded.** Accept that recommendation, then reload. Run `RUN_ID=<id> $V api home-decide POST /api/recommendations/<id>/decisions '{"action":"accept","decidedById":1}'` with the `id` from `home-rec.http.txt` (`201 Created`), then `RUN_ID=<id> $V browser goto / expect-text "Decisions needed: 0" snap home-decision-recorded`. The Kansas City row reads `<posture label> As of <date>, <time> UTC — Accepted`.
- **Refresh while open.** After the decision-recorded step (`Decisions needed: 0`), start `RUN_ID=<id> $V browser goto / expect-text "Decisions needed: 0" wait 70 expect-text "Decisions needed: 1" snap home-refreshed` in the background. During the wait, from another shell, run `RUN_ID=<id> $V api home-rec-yakima POST /api/facilities/3/recommendations` (`201`). The browser exits `0`, `home-refreshed.aria.yml` has the Yakima row with `Decision needed`, and `browser.log` has `net GET <API_URL>/api/map -> 200` after `step wait` with no `goto` between them.
- **Deferred.** A deferral must recheck before its recommendation's `decideBy`, and every live recommendation's `decideBy` is its facility day's notice deadline, so re-evaluating does not move it. Stage a fresh recommendation for a facility whose deadline is still open: run `RUN_ID=<id> $V api home-rec-lafayette POST /api/facilities/4/recommendations` (Lafayette, decision maker person `4`, `201`). If its `decideBy` is already past, also run `RUN_ID=<id> $V api home-rec-yakima-deferred POST /api/facilities/3/recommendations` (Yakima, decision maker person `3`, `201`) and defer that one instead. Lafayette's deadline is open from its 15:30 CDT closing to 05:00 CDT, Yakima's from its 16:00 PDT closing to 05:15 PDT; between 05:15 PDT and 15:30 CDT neither is, so report this step unreachable. Right away, defer it as that decision maker with a `recheckAt` between now and its `decideBy`, written exactly as `toISOString()` prints it: `RUN_ID=<id> $V api home-defer POST /api/recommendations/<id>/decisions '{"action":"defer","decidedById":<person>,"recheckAt":"<instant>","reason":{"category":"local_conditions","text":"Waiting on the next road report."}}'` (`201`, `"action":"defer"`). Run `RUN_ID=<id> $V db home-deferred-decisions "select id, recommendation_id, facility_id, action, recheck_at from decisions where action = 'defer' order by id"`: one row on that recommendation with the `recheckAt` you sent. Then `RUN_ID=<id> $V browser goto / expect-text "Decisions needed: <n>" snap home-deferred`, where `<n>` is one more than before: the new Lafayette recommendation counts whether it is deferred or overdue, and Yakima already counted from the refresh step. The deferred row reads `<posture label> As of … Decide in <minutes to recheckAt> Deferred`, a shorter countdown than its `decideBy` would give.
- **Missed decision.** Run it right after the deferred step, while Lafayette's newest recommendation (`home-rec-lafayette`) is undecided and past its `decideBy`, which is when that step deferred Yakima. If the deferred step deferred Lafayette, no facility has a missed deadline yet, so report this step unreachable. Run `RUN_ID=<id> $V api home-reevaluate-lafayette POST /api/facilities/4/recommendations` (`201`, a new `id`). Then run `RUN_ID=<id> $V db home-missed-decisions "select id, recommendation_id, action, decided_by_name, reason_text from decisions where facility_id = 4 order by id"`. It shows two `no_decision` rows by `Priya Raman`, Lafayette's backup: one on the staged earlier-day recommendation, written by `home-rec-lafayette`, and one on the `home-rec-lafayette` recommendation. Then `RUN_ID=<id> $V browser goto / expect-text "Decisions needed: <n>" snap home-missed-decision`, where `<n>` is the deferred step's count. The Lafayette row reads `<posture label> As of <new asOf> Decision overdue Decision needed`.
- **Re-evaluated after a decision.** Run this after the deferred step, before Fargo's `decideBy`. Run `RUN_ID=<id> $V api home-rec-fargo POST /api/facilities/2/recommendations` (`201`), then override it with a posture other than the recommended one as Fargo's decision maker (person `5`): `RUN_ID=<id> $V api home-override-fargo POST /api/recommendations/<id>/decisions '{"action":"override","chosenPosture":"<other posture>","decidedById":5,"reason":{"category":"local_conditions","text":"Plows are behind on the county roads."}}'` (`201`). Re-evaluate the same facility day with `RUN_ID=<id> $V api home-reevaluate-fargo POST /api/facilities/2/recommendations` (`201`, a new `id`), then `RUN_ID=<id> $V browser goto / expect-text "Decisions needed: <n>" snap home-reevaluated`, where `<n>` is one more than the count before the re-evaluation. The Fargo row reads `<overridden posture> Recommended: <new posture> As of <new asOf> Decide in … Decision needed`. An override is used because a re-evaluation minutes later almost always repeats the recommended posture, so after an accept the row shows the same posture and no `Recommended:` line; re-evaluating the accepted Kansas City facility (`home-reevaluate-kc`, then `snap home-reevaluated-accepted`) still shows `Decision needed` and adds one to the count. `RUN_ID=<id> $V db home-reevaluated-decisions "select id, recommendation_id, facility_id, action, chosen_posture from decisions where facility_id = 2 order by id"` shows the one override, on the first recommendation.
- **Facility link.** Run `RUN_ID=<id> $V browser goto / click link "Kansas City Area Service Center" expect heading "Kansas City Area Service Center" snap home-to-facility`. Exit code `0`; `home-to-facility.aria.yml` has header `# url: …/facilities/1`, and `browser.log` has `net GET <API_URL>/api/facilities/1 -> 200` after the `step click` line.
- **Conditions link.** Run `RUN_ID=<id> $V browser goto / click link "View conditions" expect toolbar "Map layers" snap home-to-conditions`. Exit code `0`; `home-to-conditions.aria.yml` has header `# url: …/conditions` and title `Conditions · Hack Midwest`, and `browser.log` has `net GET <API_URL>/api/map -> 200` after the `step click` line, which proves the browser (not SSR) loaded the data and CORS allowed it.
- **Header link.** Start on the task list and choose the brand link. Run `RUN_ID=<id> $V browser goto /tasks click link "Hack Midwest" expect table "Facility standing" snap home-from-header`. Exit code `0`; `home-from-header.aria.yml` has header `# url: …/` and title `Hack Midwest`.
- **Client-side load failure.** Hydrate another page, cut the browser off from the API, then go home. Run `RUN_ID=<id> $V browser goto /facilities block-api click link "Hack Midwest" expect-text "Facility standing could not be loaded." snap home-error-client unblock-api wait 70 expect table "Facility standing" snap home-error-recovered`. The `home-error-client` snapshot is at `/`, its main region holds only `- alert: Facility standing could not be loaded.`, and `browser.log` has `net GET <API_URL>/api/map -> FAILED net::ERR_CONNECTION_REFUSED`. The wait outlasts the dashboard's 60-second refresh interval (`REFRESH_INTERVAL_MS`), which the error view keeps running: with no `goto` after `unblock-api`, `browser.log` has `net GET <API_URL>/api/map -> 200` after `step wait`, and `home-error-recovered.aria.yml` has the table `Facility standing` and no alert.
- **Storage failure.** On a `STORAGE=broken` instance, run `RUN_ID=<id> $V browser goto / expect-text "Facility standing could not be loaded." snap home-error`. The snapshot's main region holds only the alert and no table `Facility standing`. `down` this instance before running any baseline recipe.

## Gotchas

- `Missed decision` never shows on a home row through the API. The missed-deadline `no_decision` is written only when the next live evaluation runs, and that evaluation becomes the shown recommendation, so the row reads `Decision needed`. A unit test covers the label.
- `goto` waits for network idle so the page is hydrated. A click before hydration does a full page load, the data comes from SSR, and no `net GET` line appears. That run proves the link, not client navigation.
- The countdown renders only in the browser and ticks each minute, so `Decide in …` differs between runs. Match its prefix, not its minutes.
- Every live recommendation's `decideBy` is the notice deadline of its facility day (05:00 local for Kansas City and Lafayette), and the facility day rolls over at closing time. Re-evaluating keeps the same `decideBy`. Once it passes, a deferral answers `422` on `/recheckAt`, and an undecided row reads `Decision overdue` and still counts. The deferred step picks a facility whose deadline is still open for this reason.
- A recommendation's posture comes from live weather, so the label on the Kansas City row varies. Compare it to `home-rec.http.txt`, not to a fixed label.
- `block-api` must come after `goto`. Blocking before the first page loads has no effect on SSR.
- The alert has no accessible name. Use `expect-text`, not `expect alert`.
- CORS allows only `WEB_ORIGIN`. Loading the site through a different host name than `localhost` (for example `127.0.0.1`) makes the client fetch fail and shows the load-failure alert. Always pass paths to `goto`, not absolute URLs.
